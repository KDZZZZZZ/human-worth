## 1. 产品概述

平台围绕人类与 agent 的作品比较组织内容。用户从推荐首页发现任务，提交带双方作品的新任务，或向任何公开可见任务追加一方作品。作品通过审核即允许展示，没有另一个公开/私有开关；投票时一次展示该任务全部过审作品，由用户单选一件最认可的作品。

用户也可以跳过投票直接查看统计，代价是永久放弃该账号在该任务上的后续投票权。网站与 MCP 使用相同的资格记录。平台管理员在独立的 Dashboard 中进行日常审核，并管理打包、执行和排序三个角色的挑战流程。

公开看板与热度排行榜位于同一页面，用于观察整体差距及热门任务。推荐首页的排列由平台推荐规则决定，排行榜的排列由热度决定。

## 3. 用户与权限

| 主体 | 可以完成的事情 | 边界 |
| --- | --- | --- |
| 平台用户，包括任务发布者 | 浏览推荐与任务、提交新任务、向任何可见任务追加作品、按资格投票、显式查看统计 | 不能控制云端挑战；任务作者没有批准他人追加的专有权限 |
| 本地 MCP 用户 | 使用自己的 token 阅读公开内容，显式请求投票统计 | 不代为投稿或投票；读取统计会改变同一账号的该题投票资格 |
| 平台管理员 | 使用管理员 Dashboard 审核、处理举报和下架、启动与管理云端挑战、复盘结果 | 管理入口与公开看板分开；所有管理操作关联管理员身份与结果 |
| 云端打包 / 执行 / 排序 agent | 按 H5、H7 在管理员初始包上补充执行提示、执行任务、排序作品并优化 | 输入按角色隔离；最终作品仍须审核，内部排序不取代真人投票和系统结论 |

来源：S2、S3、S4、S5。后续 H3 明确增加 Google 登录；首次登录建号为技术提案，MCP token 发放和管理员授予见待定项。

**权限相互独立：** 用户失去某题投票权后，仍可追加该题作品；投稿不会恢复投票资格。任务作者和其他普通用户都不能启动、取消、重跑或配置云端挑战。来源：S3.4、S4.3～S4.7。

## 4. 端到端交互场景

### 场景一：从推荐首页发现任务

1. 用户打开首页，直接进入平台推荐的发现流，向下滚动连续加载已发布任务。
2. 卡片展示任务摘要和允许公开的信息，不预取单题具体投票统计，不影响投票资格。
3. 用户进入任务详情，按自己的资格选择投票，或明确选择查看统计并永久放弃该题后续投票权。
4. 用户进入“看板与排行榜”页面，在同一页查看整体差距和按热度排列的任务。

### 场景二：提交双方作品、审核后发布

1. 发布者填写任务信息，至少提交一件人类作品与一件 agent 作品，可使用文件、压缩包、链接等形式。
2. 在各作品的上传表单中记录来源、相应授权和配置；缺少任一方作品时可以保存草稿，但不能送交发布审核。
3. 任务及双方初始作品一起进入待审核；官方审核通过后公开，驳回则说明原因并允许修改重提。
4. 已发布任务进入推荐候选、公开查询与真人投票；用户提交任务不启动云端 agent。

### 场景三：所有用户向任何可见任务追加作品

1. 任意用户打开任意公开可见任务即可选择追加人类或 agent 作品，无需是任务发布者，无需任务作者邀请或批准，也无需同时提交另一方。
2. 任务可见即表示任务本身已通过审核；追加投稿不会让已有任务重新送审，任务保持已发布状态。
3. 投稿者上传作品并设置该件作品的授权或配置；只有新增作品按自己的发布流程送审，通过后加入公开参选列表，驳回时向投稿者反馈原因。
4. 该用户即使已因查看统计而失去这道题的投票权，也仍可追加作品；投稿不恢复投票资格。MCP 仍只提供内容读取，不代为投稿。

### 场景四：平台管理员通过 Dashboard 日常审核并管理云端挑战

1. **进入每日工作台。** 平台管理员登录管理员 Dashboard，查看待审核任务与作品、举报、云端挑战状态、异常和额度使用情况。该页面与公开的看板 / 排行榜分开，普通用户无管理权限。
2. **处理日常审核。** 管理员审核新任务及双方初始作品、独立追加作品和云端生成作品，执行通过、驳回及原因反馈，按需要处理举报和下架。任何公开可见任务本身已过审，不因新投稿重复审核原任务。
3. **启动云端挑战。** 管理员在 Dashboard 选择已公开可见任务、生成者 / 投票者配置及轮数与预算，确认材料可用后启动。任务作者及其他普通用户均不能执行这一步。
4. **查看运行过程。** Dashboard 展示阶段、轮次、配置和消耗；待定任务只追加生成，agent 领先任务可提炼经验，人类领先任务准备授权材料、验证投票者，再按匿名对抗流程运行。
5. **处理失败与停止。** 模型失败、预算不足或材料失效时，管理员查看原因并按规则取消或重新启动；重新启动创建关联的新运行并重新检查任务、授权和额度。取消或结束后的迟到结果不继续推进，也不登记新作品。
6. **处理产出与发布。** 最终候选进入 Dashboard 的作品审核待办，通过后公开并开放真人投票。登记响应丢失或重试时先找回已有作品及审核状态，避免重复作品和绕过审核。
7. **复盘与后续安排。** 管理员查看运行结果、审核记录和有效真人反馈；系统独立计算任务状态与翻转，管理员据此安排后续挑战。操作身份和结果均留存，普通用户只能查看允许公开的进度。

本场景统一覆盖管理员的日常审核、挑战启动、过程管理、取消、失败处理和登记重试。

### 场景五：通过 MCP 查看统计并永久失去该题投票权

1. 用户通过自己的 token 调用 `list_tasks` 和默认 `get_task` 阅读公开内容，不影响投票资格。
2. 用户明确选择读取该题投票统计，客户端说明永久失去该题投票权的后果后提交显式统计请求。
3. 平台先按账号与任务保存永久资格变化，再返回统计；统计请求本身不提交选票。
4. 该账号之后在网站也不能再投这道题，换 token、换作品对或新增作品均不恢复；其他任务的资格不受影响。
5. 网站用户通过“跳过投票并查看统计”入口执行相同流程。

### 场景六：看板与热度榜同页查看

1. 用户在一个页面看到整体差距看板和热度排行榜；排行榜按热度降序排列已发布任务。
2. 用户可直接浏览平台 / 分类汇总、任务热度与摘要；首页推荐顺序由平台推荐规则决定。
3. 点击任务进入详情；从榜单或看板下钻到该题具体得票和胜率时，仍经过 US-36 的资格变更。

<a id="human-revisions"></a>
### 4.1 人类修订 H1：审核决定展示、全部作品单选

2026-09-18，用户明确修订：“作品不分是否公开只分有没有过审允许展示，投票不是二选一而是一次给出所有作品”；随后确认：“从全部作品中选一个最认可的”。这两条为 **Human Design**，优先于原场景中的旧措辞和先前的技术提案。

- **H1.1 展示条件**：作品只按审核结果决定能否对外展示。任务可见且作品审核通过，即可展示其作品内容和关联文件；不再要求单独的公开授权，也不提供作品公开/私有设置。未过审作品只用于本人投稿管理和管理员审核，不能进入普通浏览、MCP 内容读取或投票列表。撤销审核通过后停止展示。
- **H1.2 投票展示**：一次给出该任务当前全部允许展示的过审作品，包含全部 human 和 agent 作品；不抽取两件配对，不截取部分候选让用户投票。新增作品通过审核后进入后续完整列表。
- **H1.3 单选行为**：用户从上述全部作品中选一件最认可的作品；不使用 left/right/tie，也不是分别评分或多选。普通展示与投票结果仍不返回具体统计。

原始场景保留作为历史依据，原文中的“作品公开/发布”在现行需求中表示“作品通过审核、允许展示”；“换作品对”不再对应现行产品入口。原有统计访问先永久关闭账号×任务投票资格的规则继续有效，更换 token、刷新候选列表或新增作品均不恢复资格。云端使用授权是另一用途的许可，不决定作品能否展示。

完整列表的版本校验、每账号每任务的当前选票、改选与幂等策略属于 [OpenAPI 技术提案](../openapi.yaml)，跨服务边界见[架构划分](backend-architecture.md)；这些不是此次人类追加确认的规则。

<a id="hide-quota"></a>
### 4.2 人类修订 H2：不再显示额度

2026-09-18，用户在了解管理员概览的额度含义后明确要求：“不要再显示额度了”。管理员概览和运行列表/详情不再展示额度余额、已用额度及消耗数值。原始场景保留用于溯源，其中 S4.1 的“额度使用情况”和 S4.4 的“消耗”展示要求由 H2 覆盖。

实施范围说明（Agent Self-Claimed）：移除展示响应中的 `AdminDashboard.quota`、`ChallengeRun.consumed`，后续 Proto 同样不提供这些展示字段。原有启动/重启时的预算配置、后台执行限制与内部结算继续保留，本次展示修订不扩展为取消预算控制。

<a id="google-login"></a>
### 4.3 人类修订 H3：增加 Google 登录

2026-09-18，用户明确要求：“为啥 openapi 没有登录啊，加一个谷歌登录”。支持 Google 登录为 **Human Design**；原六个可信场景保持原文。

实施方案（Agent Self-Claimed）：采用服务端 Google OIDC 授权码流程，补充登录入口、回调与当前会话退出接口；首次有效登录创建普通账号，再次登录复用稳定账号。具体 Cookie、PKCE、超时、字段与内部 RPC 见 [OpenAPI](../openapi.yaml) 和 [Identity 设计](backend-identity.md)。2026-09-19 已实现并发布，用户已确认真实 Google 登录成功；证据范围见[部署记录](deployment.md#identity-lab)。

登录、退出和换凭据不恢复账号在某任务上的永久禁投资格；Google 资料不自动赋予平台管理员权限。其余产品边界继续适用。

<a id="challenge-prompt-optimization"></a>
### 4.4 人类修订 H4：挑战隔离与提示词优化（角色由 H5 修订）

用户先提出“我们要给每一个挑战任务做隔离”，并补充：“还得设计一下两个对抗agent，你可以参考强化对抗的思路只不过优化的是提示词”。任务隔离与提示词优化要求继续有效；其中角色数量与分工以随后明确的 H5 为准，不据此扩大为训练模型权重或改变真人投票规则。

上一版由 agent 推导的双角色设计已被替换，现行方案见 [Challenge 设计](backend-challenge.md)。S4 的管理员权限、审核与真人反馈边界继续适用；按结论分流的安排由 H9 覆盖。

<a id="challenge-three-agents"></a>
### 4.5 人类修订 H5：打包、执行、排序三个角色

用户明确修订：“应该是三个agent，输入分为任务描述（包括附件）和作品”；要求执行 agent 只根据任务包生成作品，排序 agent 按好坏排序所有作品。最初由打包 agent 准备初始包的安排，随后由 H7 改为管理员手工准备；打包 agent 继续优化执行提示。

- **打包 agent**：初期允许读取用户评论的安排已被 H10 覆盖，当前不接收任何用户评论。可见管理员初始包及自己任务包生成的作品、报告、名次，并按 H10 接收合格 R 的自身作品评判依据与拟合度，不能看其他作品。用户先补充作品与轨迹，随后修订为“先只看到作品吧，让工作agent做一个报告，让打包agent能看到关键决策和最终结果”，因此采用作品与执行报告反馈，不读取完整轨迹；优化任务包让自己的排名尽量靠前。
- **执行 agent**：只接收任务包，负责把任务做好，不参与跨轮策略优化。
- **排序／评审 agent**：可见任务描述及附件、用户评论和全部作品，不能看任务包；评审结果尽可能拟合真人投票。

用户还提出：“其实只需要生成作品的agent需要真正工作区甚至真正的harness，另外两个都可以简化成模型调用对吧”。随后否定共享只读工作区的方案：“不需要，反正作品已经必须是文字或者文件，作品能够提交就说明可以让打包agent和审查agent看见”。直接复用作品的文字／文件作为模型输入，执行角色使用隔离工作区和 harness；多轮推进由服务端控制。打包与排序的模型调用方式由 H11 补充为可按需使用 ReAct，不再限定为无工具调用。

上述角色、信息边界与优化目标为 **Human Design**。`report.md`、统一文字／文件输入适配、禁止排序者读取执行报告以免间接读到任务包、Voting 受限训练快照与评价参数属于 [Challenge 技术提案](backend-challenge.md#work-feedback)。作品支持文字及文件，链接可作为补充说明，但不能只交外链让评审自行抓取。无法读取的文件必须明确处理，不能把只有文件名或摘要当成已读作品。真人仍从全部过审作品单选一件；内部排序不改变 H1，也不提供绕过永久禁投资格的用户统计入口。

<a id="remove-challenge-progress"></a>
### 4.6 人类修订 H6：删除普通用户挑战进度入口

用户明确要求：“/api/tasks/{taskId}/challenge-progress 不需要”。删除这一接口及仅为它设置的内部 RPC 和响应类型；不增设替代的普通用户进度入口。管理员仍通过运行列表和详情查看状态。S4 中普通用户查看公开进度的历史安排由此覆盖，原场景保留不改。

<a id="manual-initial-package"></a>
### 4.7 人类修订 H7：管理员手工准备初始包和作品要求

用户明确要求：“打包和执行agent不能看见其他作品不然就会作弊，算了先让管理员手工给一个初始的包吧，从用户的任务描述里选择文件然后手写描述和作品要求”。管理员选择任务描述的附件、手写执行说明和作品要求，P/E 不能读取其他参赛作品。P 仍可接收自己任务包生成的作品、报告和名次反馈。

技术方案将说明、选定附件和作品要求保存为不可变初始包，随启动／重启提交；P 只改执行提示，E 接收固定部分加执行提示。初始包改动需新 Run；服务端校验任务版本和附件归属，管理员负责说明忠实与选材完整。R 仍看原始任务与全部作品，不看初始包。这些字段与冻结机制属于 [Challenge 技术提案](backend-challenge.md)，本轮不增加管理员前端页面。

<a id="simple-challenge-iteration"></a>
### 4.8 人类修订 H8：简化迭代，取消回滚与版本保留

2026-09-20，用户要求：“退化回滚，保留版本，去掉相关的逻辑，保持简单”。Challenge 不保留历史任务包／排序提示词版本，不做退化回滚、版本晋升或新旧择优。

技术方案仅维护当前任务包与排序提示，按 H10 分阶段改写，格式和权限校验通过后直接覆盖，用于后续执行；正常结束登记最后完成一轮的有效作品。作品、报告、运行状态及幂等回执仍按业务需要保留。此前技术提案中的版本树、固定旧提示对照与退化回滚要求由 H8 覆盖；H10 的拟合门槛用于决定能否开始优化 P。

<a id="challenge-unified-goal"></a>
### 4.9 人类修订 H9：Challenge 统一追求最佳效果

2026-09-20，用户明确修订：“你管他谁领先，challenge的目标都是一样的，就是成为最好的或者和最好的效果对齐”。所有 Challenge 都以产出最佳作品、或达到与最佳作品相当的效果为目标；任务结论待定、人类领先或 agent 领先，均不改变这一目标和运行流程。

本修订覆盖 S4.4 及派生要求中的按结论分流，原始场景保留用于溯源。系统根据真人反馈计算任务结论，仍用于差距展示与复盘；Challenge 的优化流程不依赖谁领先。H5、H7 的角色输入边界和 H8 的简单迭代继续有效。

技术方案移除 Challenge 的任务结论 DTO、读取依赖与分流字段；统一目标下，具体迭代顺序以 H10 的先 R 后 P 为准。名次是改进信号，运行完成不等于已达到最佳；效果仍须通过作品比较和真人反馈验证。

<a id="ranker-before-packer"></a>
### 4.10 人类修订 H10：P 不看评论，先得到合格 R 再优化 P

2026-09-20，用户明确修订：“任何用户评论都不能对P可见”，并要求“R需要给出评判依据和获得的人类偏好拟合度”；“低于阈值时我们只迭代R，高于阈值时先使用这个能力强的R评测E的作品只迭代P并运行E”，总目标是“先得到一个善于排名的R，再得到优秀的P”。

- P 不接收任何用户评论，也不能通过任务包、评判依据或其他反馈转交评论。
- R 输出排名与评判依据，并取得对照真人偏好的拟合度。未超过阈值时只迭代 R，使用反馈改进其排序能力；P 不迭代，E 不运行。
- 拟合度超过阈值后固定合格 R，使用它评测 E 的作品，以评判依据和拟合度支持 P 改进执行提示，再运行 E；此阶段只优化 P，不同时改写 R。
- H9 的统一目标、H7 的固定初始包和 P/E 不看其他作品、H8 不保留历史提示及不回滚继续有效。

以上为 Human Design，覆盖原有向 P 提供评论、每轮交替改写 P/R、样本不足仍推进 P/E 的安排。技术方案以可信评分器计算的拟合度作为门槛，阈值随启动配置提交；等于阈值时不放行，样本不足不能判定达标。拟合指标、数据划分、反馈投影与状态字段是 [Challenge 技术提案](backend-challenge.md#ranker-calibration)，本修订未指定具体阈值数值。

<a id="challenge-react-tools"></a>
### 4.11 人类修订 H11：P/R 按需使用 ReAct，工具保持精简

2026-09-20，用户明确补充：“其实R和P可以视情况使用react，你根据需要设计他们的工具，不要无脑设计一大堆”。结合三角色上下文，此处按 ReAct 的推理与工具调用循环设计；P/R 可以在有需要时使用工具，不要求每次调用都走多步循环。

工具只为实际步骤服务，继续遵守 H7、H10 的角色信息边界和先 R 后 P 的迭代顺序。技术方案先提供一个共享的 `read_material`，按角色及本次用途读取获准材料；输入已足够时直接返回结果。工具名称、权限投影、循环限制及不增加外部配置属于 [Challenge 技术提案](backend-challenge.md#minimal-react-tools)，不是人类指定的工具清单。

## 5. 功能需求

### FR-01 推荐发现首页

来源：S1.1～S1.4、H1.2～H1.3。

1. 网站首页直接展示平台推荐的任务发现流，向下滚动连续加载已发布任务。
2. 任务卡片提供标题或摘要及允许公开的信息，用户可以进入任务详情。
3. 卡片和预加载不读取单题具体投票统计，不影响用户的投票资格。
4. 用户进入投票时一次看到该任务全部过审且允许展示的作品，从中单选一件最认可的作品；也可明确选择查看统计并永久放弃该题后续投票权。投票列表不得抽样、两两配对或只展示第一页候选。
5. 首页可进入看板与排行榜共用的页面。推荐规则的具体算法与参数待定。

### FR-02 提交双方作品并发布新任务

来源：S2.1～S2.4、H1.1、H5。

1. 创建任务时填写任务信息，至少提交一件人类作品和一件 agent 作品。
2. 作品以文字和／或文件交付，文件可包含压缩包；链接可以作为补充说明，不能代替实际作品内容。上传记录各作品的来源、相应授权和配置。
3. 缺少任一方作品时可以保存草稿，但不能送交发布审核。
4. 任务与双方初始作品一起进入待审核；管理员审核通过后任务可见、初始作品允许展示，无需再次选择公开或授权公开；驳回时给出原因并允许修改重提。
5. 发布后的任务可以进入推荐候选、公开查询与真人投票。用户提交或发布任务不启动云端 agent。

文件白名单、大小限制、云端使用授权细则以及配置字段的完整结构未由该场景定值；这些细则不能引入作品公开/私有开关。

### FR-03 所有用户追加任意可见任务

来源：S3.1～S3.4、H1.1～H1.2。

1. 任意用户都可以向任意公开可见任务追加人类作品或 agent 作品，无需是发布者、无需作者邀请或批准，也无需同时提交另一方。
2. 可见任务本身已通过审核。追加作品不使任务重新送审，原任务保持已发布状态。
3. 投稿者上传新作品并记录来源、云端使用授权及适用配置；只有新作品进入自己的审核流程。
4. 新作品审核通过后即允许展示，并进入该任务的完整参选列表；不设置独立公开状态。驳回时向投稿者说明原因。
5. 已因查看统计失去该题投票权的用户仍可追加作品；追加不恢复投票资格。
6. MCP 只提供内容读取，不代为追加投稿。

### FR-04 管理员 Dashboard 与云端挑战管理

来源：S4.1～S4.7、H2、H4～H11。日常审核、启动、取消、失败处理与重试属于同一个管理员工作场景。

#### FR-04.1 每日工作台

- 平台管理员登录独立的管理员 Dashboard，查看待审核任务与作品、举报、云端挑战状态及异常，不显示额度余额或已用额度。
- Dashboard 与公开看板 / 排行榜分开；普通用户没有管理权限。

#### FR-04.2 日常审核

- 审核对象包括新任务及双方初始作品、独立追加作品和云端生成作品。
- 管理员可以通过或驳回并反馈原因，按需要处理举报和下架。
- 公开可见任务本身已经过审，不因追加投稿而重复审核原任务。

#### FR-04.3 启动挑战

- 只有平台管理员可以在 Dashboard 中选择公开可见任务，选定任务附件、手写初始说明及作品要求，再选择三角色配置、拟合阈值、两阶段轮数和预算，确认材料可用后启动。
- 任务作者及其他普通用户不能执行启动操作；用户发布内容不是云端启动入口。

#### FR-04.4 运行观察与统一目标

- Dashboard 显示当前阶段、轮次和配置，不显示消耗数值。
- 所有挑战都追求成为最佳作品，或达到与最佳作品相当的效果，不按人类／agent 谁领先分流。
- 准备授权材料后先单独迭代 R，输出评判依据并计算真人偏好拟合度；超过阈值后固定 R，再执行 P 改提示→E 生成→R 评测→反馈 P 的循环。
- 样本不足或拟合未达标时不启动 P/E；可观察当前阶段、R 拟合度及两阶段轮次。

统一目标来自 H9，先 R 后 P 与拟合门槛来自 H10；材料结构、拟合指标与迭代细节见 [Challenge 技术提案](backend-challenge.md)，不将实验参数视为已确认的产品规则。

#### FR-04.5 异常、取消与重新启动

- 模型失败、预算不足或材料失效时，管理员可以查看原因并按规则取消或重新启动。
- 重新启动创建关联的新运行，重新检查任务、授权和额度，不覆盖原运行。
- 取消或结束后的迟到结果不能继续推进，也不能登记新的作品。

#### FR-04.6 产出审核与登记重试

- 最终候选进入作品审核待办；审核通过后允许展示并加入全部作品单选列表，遵循 H1，不额外设置公开开关。
- 登记响应丢失或重试时，先找回已有作品及审核状态，避免重复作品和绕过审核。
- 生成完成、作品登记、审核发布和真人反馈分别体现，不能混写为同一个“获胜”结果。

#### FR-04.7 复盘与后续安排

- 管理员查看运行结果、审核记录和有效真人反馈。
- 系统独立计算任务状态和翻转，管理员据此安排后续挑战。
- 记录操作身份和结果；按 H6 仅保留管理员运行列表／详情，不提供普通用户挑战进度接口。

#### FR-04.8 三角色任务包优化、排序拟合与隔离

来源：H4、H5、H7、H8、H9、H10、H11；具体优化流程见 [Challenge 设计](backend-challenge.md#adversarial-agents)。

- 输入区分原始任务描述及附件、作品和评论；任务附件不从作品文件隐式推导。
- 管理员选定任务附件、手写初始说明与作品要求；P 用初始包、自身作品／报告、名次及合格 R 的评判依据和拟合度改进执行提示，不接收任何用户评论、其他作品或改动初始要求。E 只按本次包产出并报告关键决策与最终结果；R 看全部作品但看不到任务包和执行报告。
- 第一阶段只用真人偏好监督迭代 R；拟合度超过阈值后冻结 R，第二阶段只迭代 P 并运行固定配置的 E，由固定 R 评测。只维护当前提示，不保留历史提示版本或退化回滚；作品、报告、评判依据、拟合证据和必要运行记录仍保留。
- 打包与排序用受控模型调用，可按需通过精简工具进行 ReAct，输入足够时直接返回；执行者用独立工作区与 harness。工具读取遵守本次用途和角色的信息边界，不改变先 R 后 P 的流程。
- 排序必须覆盖完整作品集合，不产生平台真人选票、不跳过审核；所有任务统一追求最佳或对齐最佳效果。

### FR-05 MCP 与直接查看统计

来源：S5.1～S5.5，并与 S1.2～S1.3、S3.4、S6.3 一致。

1. 用户使用自己的 token 调用 `list_tasks` 和默认 `get_task` 阅读公开内容，不影响投票资格。
2. 查看单题投票统计须显式提出；客户端先说明永久失去该题投票权的后果，再提交统计请求。
3. 平台先按“账号 × 任务”保存永久资格变化，再返回统计。请求本身不产生任何选票。
4. 此后同一账号在网站也不能再投这道题；更换 token、刷新候选列表或新增作品均不恢复资格，其他任务不受影响。
5. 网站提供“跳过投票并查看统计”入口，并执行相同流程。
6. 普通读取和显式统计读取须区分，不能把两者都描述为无副作用；统计请求的具体参数与返回结构待定。

| 读取方式 | 用户得到什么 | 对该题投票资格的影响 |
| --- | --- | --- |
| `list_tasks` / 默认 `get_task` | 允许公开的任务内容 | 不改变 |
| 显式请求单题投票统计 | 在说明后果后读取统计 | 先永久关闭该账号的后续投票资格，再返回统计 |
| 网站跳过投票看统计 | 与 MCP 相同的统计访问路径 | 与 MCP 共用永久资格记录 |

### FR-06 看板与热度排行榜同页

来源：S6.1～S6.3，并与 S1.4 一致。

1. 一个页面同时呈现整体差距看板和热度排行榜。
2. 排行榜只排列已发布任务，按热度降序；首页仍由平台推荐规则决定顺序。
3. 用户可直接浏览平台 / 分类汇总、任务热度与摘要。
4. 点击任务进入详情；从榜单或看板查看该题具体得票或得票占比时，也必须经过 FR-05 的资格变化流程。历史场景中的“胜率”按 H1 的全部作品单选语义由得票占比承接。
5. 热度计算、推荐规则、统计窗口与刷新频率未在场景中定值；不能自行引入固定权重或得票占比排行。

### FR-07 Google 登录与当前会话

来源：H3；会话与账号约束继承 S2～S5。下列流程细节按 H3 的技术方案设计。

1. 网站提供 Google 登录入口；认证成功后建立 Human Worth 网站会话，前端可以查询本人身份和 CSRF token。
2. 首次有效登录创建普通账号，再次登录保持相同账号 ID；退出当前会话不删除账号、投稿、选票或禁投资格。
3. 用户取消或登录失败时给出明确结果，不假报成功。管理员角色由平台授予，Google 邮箱或资料不能替代该授权。
4. 浏览器不保存 Google token；MCP 继续使用专属读取凭据，不通过登录回调获取额外能力。

## 6. 状态流转与业务不变量

以下是对场景行为的整理，不指定存储结构或接口实现。

| 对象 | 场景要求的流转或关系 | 来源 |
| --- | --- | --- |
| 新任务及双方初始作品 | 可存草稿 → 双方齐备后送审 → 通过后任务可见、初始作品允许展示；驳回后说明原因、允许修改重提 | S2.1～S2.4、H1 |
| 追加作品 | 上传并记录云端授权 / 配置 → 仅新作品送审 → 通过后允许展示并加入完整参选列表，原任务保持已发布 | S3.1～S3.3、H1 |
| 云端最终作品 | 生成候选 → 管理员审核待办 → 审核通过 → 允许展示并加入完整参选列表 | S4.6、H1 |
| 云端运行 | 管理员启动、观察、取消或按规则重启；重启产生关联的新运行，终止后的迟到结果无效 | S4.3～S4.5 |
| 账号在任务上的投票资格 | 满足现有投票条件 → 显式查看统计时永久关闭后续投票资格 → 返回统计 | S5.1～S5.5 |
| 任务对比结论 | 系统根据有效真人反馈独立计算待定 / agent 领先 / 人类领先及翻转，用于差距展示与复盘；不决定 Challenge 的目标和流程 | S4.7、H9 |

必须保持的关系：

- **公开可见意味着任务已经过审。** 投稿追加不重审原任务。
- **作品展示由审核决定。** 任务可见且作品过审即可展示；没有独立的公开/私有状态或公开授权开关。撤销通过后立即退出展示与投票列表。
- **全部作品单选。** 投票页一次展示全部允许展示的过审作品，用户从中单选一件；同一列表包含任意数量的人类和 agent 作品。
- **审核通过与作品胜负分别处理。** 生成或发布完成不替代真人投票及系统结论。
- **投稿权限与投票资格分别处理。** 永久失去某题投票权不阻止追加作品，追加也不恢复资格。
- **内容读取与统计读取分别处理。** 普通阅读不触发资格变化；显式统计读取必须先记录变化再返回结果。
- **任务发布与云端启动分别处理。** 云端执行由平台管理员在 Dashboard 控制。

| 入口 | 主要内容与动作 | 来源 |

| Google 登录 / 退出 | 跳转 Google 完成认证、查看本人会话、退出当前网站会话 | H3；流程细节为技术方案 |
